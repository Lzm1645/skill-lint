## 1. 方法与可复现性

- **怎么选样**：用 GitHub 搜索（`agent skills`、`claude skills`、`SKILL.md`、`dsh skill`、topic `dsh-skill`）拉候选，只保留至少含 1 个 `SKILL.md` 的仓库；排除 3 个没有 `SKILL.md` 的目录/清单型仓库（`Whning0513/awesome-deepseek-skills`、`MengYuil/dsh-ponytail`、`BehiSecc/awesome-claude-skills`）；不纳入声称 1.8 万个自动生成 skill 的库，避免单仓库主导分布。
- **扫描单元**：一个目录里有 `SKILL.md` 就算一个 skill；跳过 `vendor/`、`node_modules/`、`.git/` 等目录（因此 1,348 比 `find` 数出的 1,352 少 4 个 vendored skill）。
- **固定版本**：`scan/repos.json` 固定每个仓库的 commit；`scan/results-2026-11-19.json` 记录扫描时的工具 commit 与 `skill_lint.py` 的 sha256。
- **纯静态**：不执行 skill 代码，不访问网络；判定基于文本启发式。
- **复跑**：

```bash
python3 scan/scan_public.py --config scan/repos.json --json /tmp/scan.json
```

## 4. 高频风险模式（带证据）

### 4.1 能力边界不可见：`allowed-tools` 声明率 0.6%

`anthropics/skills/skills/pdf/SKILL.md` 的 frontmatter 只有 `name`/`description`/`license`，没有 `allowed-tools`；全语料只有 8 个 skill 声明了它。这比任何单条“危险命令”都更系统性：agent 拿到 skill 后无法从声明判断它能读什么、写什么、连哪里。

### 4.2 出处与许可缺失：74%

1,000 个 skill 的 `SKILL.md` 没有 `repo`/`license`/`provenance` 字段。在 27 个仓库里都能看到：skill 可以被复制、改写、再分发，但无法追溯来源。

### 4.3 远程脚本管道执行：25 个 block

真实安装指令，不是文档示例：

- `google/skills/skills/cloud/developing-genkit-go/SKILL.md:139`：`curl -sL cli.genkit.dev | bash`
- `realchendahuang/dsh-skill/README.en.md:29`：`curl -fsSL https://raw.githubusercontent.com/.../install.sh | bash`
- `Jeffallan/claude-skills/.../kubernetes-specialist/SKILL.md:9`：`curl -L https://istio.io/downloadIstio | sh -`

在 CI / 无人值守场景里，这三条都等价于“让远端决定这台机器执行什么”。

### 4.4 敏感读取：66 个 block

按“同一行必须有读取动作”过滤后仍然命中，例如：

- `alirezarezvani/claude-skills/.../coding-agent-rollout/assets/managed-settings.example.json:5`：`"Read(./.env)"`（示例配置里允许直接读 `.env`）
- `mrgoonie/claudekit-skills/.claude/skills/.../troubleshooting.md:429`：`env | grep CLAUDE`（把环境变量导到输出）
- `google/skills/skills/cloud/secops-cases/SKILL.md:50`：安全调查流程里要求读取 `~/.ssh`、服务账号 key（安全场景的“读取”是任务本身，但仍是高风险能力）

### 4.5 破坏性命令无确认：35 个 block

- `google/skills/skills/cloud/gke-batch-hpc/SKILL.md:98`：`kubectl apply --server-side -f …`
- `anthropics/skills/skills/docx/SKILL.md:57`：`(cd unpacked && rm -f ../out.docx && zip …)`（构建清理，但确实是删文件）
- `alirezarezvani/claude-skills/.../terraform-patterns`、`senior-devops`：`terraform apply` 类命令

### 4.6 出网：123 个 block（集中在安全研究类）

74 条在 `elementalsouls/Claude-BugHunter` 的披露报告/攻击样例里（`169.254.169.254`、`metadata.google.internal`、`127.1`、`0177.0.0.1`），其余在 alirezarezvani 的 SSRF 模式类 skill。**这些是“演示攻击”还是“指示 agent 发起攻击”，静态检查区分不了**——报告把它们计为命中，但不建议把这类仓库整体判为恶意。

同一规则下另有 105 条 warn：文档里引用的 http 链接（例如 `Alice39s/agent-stash/skills/code-styleguide/references/google/pyguide.md`），已不再 block。

### 4.7 写 settings / hooks：13 个 block

- `alirezarezvani/claude-skills/.../commit-craft/SKILL.md:53`：`Install assets/hooks/ to run steps 2 to 4 on every commit and push.`
- `cursor/plugins/.../setup-benny/SKILL.md:34`：`Add pstack to the target repository's .cursor/settings.json`
- `mrgoonie/claudekit-skills/.../skill-creator/SKILL.md:46`：`Add to .claude/settings.json:`

这类 skill 会修改 agent 自身的持久配置，属于供应链风险面，block 是设计意图。

### 4.8 注入面与外部内容边界（warn）

L06 252 条命中 `shell=True`/`eval`/`exec`，多数出现在示例代码或正常脚本里；L08 224 条是抓网页/日志但没有写「数据非指令」。两者作为 warn 合适，不升级为 block。

## 5. 误报审计与规则收敛

方法：对每条 block 找到源行（`path:line`），区分「文档里提到」「示例/占位符」「真实能力」。只改有大量证据的规则，改动都补了 fixtures 回归测试。

| L07 破坏性命令 | 469 | 35 | 0 | 0 |

### 5.1 L03：XML 命名空间不是出网目的地（595 → 123）

收敛前 595 条 block 的分类：

| 类别 | 条数 |
|---|---:|
| 其他（真实 http URL / IP） | 154 |
| `schemas.openxmlformats.org` 等 XML 命名空间 | 114 |
| 单标签/内网主机名（`marquez:5000`、`your-cache-server.internal`） | 105 |
| 云元数据 / SSRF 样例（`169.254.169.254`、`metadata.google.internal`） | 79 |
| 模板/正则片段（`http://{short}`、`http://$NODE_IP`） | 43 |
| 其他 schema（sitemaps/idpf/json-schema/openoffice） | 26 |
| `schemas.microsoft.com` | 24 |
| `example.com` 占位域名 | 23 |
| `www.w3.org` 命名空间 | 21 |
| `schemas.android.com` | 6 |

改动：

- 跳过 XML 命名空间 host、`*.example.*` 占位域名、`.internal` 内网主机、单标签主机、模板/正则 URL；
- frontmatter 里的 `repo`/`license` 链接视为出处元数据，不算出网；
- 代码块（```/~~~）里的 http/IP 才 block；文档引用里的 http 降为 warn。

真阳性没有丢：云元数据地址、真实 http 安装脚本、`webhook.site`/`ngrok` 等仍按原级别报告（`bad-remote` fixture 仍 block）。

### 5.2 L04：文档里的 `.env` 不是读取（826 → 66）

收敛前 826 条 block 中 654 条是 `.env` 关键词命中，典型误报：

- `addyosmani/agent-skills/.../ci-cd-and-automation/SKILL.md:277`：`.env.example → Committed (template for developers)`
- `.../context-engineering/SKILL.md:65`：`Never commit .env files or secrets`
- `.../git-workflow-and-versioning/SKILL.md:248`：`.gitignore ... .env, .env.local`
- deny 规则 / 检测器正则里的 `~/.ssh`、`id_rsa`、`\.env`（例如 `settings_linter.py` 的 `"deny": ["Read(./.env)"]`）

改动：

- 敏感路径必须与读取动作同现（`cat`/`open(`/`Read(`/`source`/`grep`/`dotenv` 等）；
- 文档/防护/占位语境（`never`、`don't`、`gitignore`、`deny`、`template`、`.env.example`、`regex`、`***`）跳过；
- `env |` 只在后接真实管道命令时才报，修掉 markdown 表格里 `env | Medium` 的误命中。

代价：只“提到”敏感路径、却没有读取动词的 prose 不再报；这是有意的精度取舍。

### 5.3 L07：散文里的 deployment 不是部署（469 → 35）

收敛前 469 条 block 覆盖 34.8% 的 skill，命中词统计：deploy 413、write 224、apply 135、update 124、delete 104、remove 85、manage 68。绝大多数是说明文字：

- `addyosmani/agent-skills/.../ci-cd-and-automation/SKILL.md:3`：`description: ... setting up or modifying build and deployment pipelines`
- `.../documentation-and-adrs/SKILL.md:25`：`ADRs capture ... the highest-value documentation you can write.`
- `.../api-design/SKILL.md:227`：`PATCH /api/tasks/:id → Update a task (partial)`

改动：只对“会实际执行的破坏性命令”报 block（`rm -rf`、`git push`、`kubectl apply/delete`、`terraform apply/destroy`、`docker push`、`npm publish`、`DROP TABLE` 等），并要求同一 skill 里没有 confirm/dry-run。散文里的 update/write/deploy 不再命中。

代价：非破坏性的文件写入（例如让 agent 用 Write 工具改文件）不再 block；这属于更细的“确认门”设计，留待后续规则。

### 5.4 L10：settings/hooks 写入要“动词在目标附近”（117 → 13）

收敛前 117 条里大量是：

- `alirezarezvani/claude-skills/.../c-level-advisor/.../SKILL.md:139`：`Migration: a legacy memory/... folder may exist ... write new transcripts`
- `.../coding-agent-rollout/.../settings_linter.py:111`：`p.add_argument("--managed", help="...settings.json")`（argparse 帮助文本）
- `.claude/decision-log.md` 这类数据文件写入（不是 settings/hooks）

改动：目标收窄为 `settings.json`、`.claude/settings|hooks|config`、`.cursor/settings|hooks`、`.codex/config`、`*/hooks/`，并要求写入动词出现在目标前 60 字符内；`webhooks/` 不再误命中。

收敛后剩下 13 条：其中 8 条来自 alirezarezvani 仓库内重复的 skill 目录（`engineering/` 与 `engineering/skills/` 各存一份，内容相同），去重后约 9 条；9 条里 8 条是“把 hook 装进 settings”的真实指令（commit-craft、cursor/setup-benny、google-ads-mcp-setup、skill-creator、using-superpowers），1 条是描述性语句（“Claude Code adds `.claude/settings.local.json` to the git excludes”），属于启发式的残余误报。

### 5.5 未改动的规则

L01（缺 `allowed-tools`）、L10（缺 provenance）保持 warn：它们反映的是生态级声明缺口，不是误报；L02/L06/L08/L09 保持原样：L02 的命中基本是真实安装指令，L06/L08/L09 是 warn 级信号，噪声可接受。

## 6. 局限

- **静态启发式**：不执行代码、不解析 AST；正则无法理解意图。安全研究类 skill 内嵌攻击 payload（SSRF、`rm -rf` 样例）会持续命中 L02/L03/L04/L07——这是规则按设计的行为，不代表仓库恶意。
- **样本偏差**：按 GitHub 搜索/star 排序取样，主流集合（anthropics、google、cursor）占比高；单个大仓库（alirezarezvani 495 个 skill，其中 28 个是重复副本、467 个唯一）会主导总量，因此报告同时给出仓库级中位数。
- **没有测漏报**：本次只审计 block 的误报，没有构造“带风险但规则未命中”的样本，召回率未知。
- **dsh 子集很小**：45 个 skill，结论只能当方向性信号；更大的 dsh 语料需要从 `awesome-dsh-skills` 目录里逐仓库抓取。
- 规则收敛偏向精度：L07 不再覆盖“写文件”类操作，L04 不再覆盖无读取动作的 prose 提及。

## 7. 建议

对 skill 作者：

1. 在 frontmatter 声明 `allowed-tools`（哪怕只是 `Read`），让能力边界可见；
2. 加 `repo`/`license`/`provenance`，让复制和再分发可追溯；
3. 安装脚本别用 `curl | bash`；必须用时固定版本 + 校验和，并写明确认步骤；
4. 破坏性命令前给 confirm/dry-run；
5. 抓网页/日志后显式声明「数据非指令」。

对 dsh 生态：45 个 skill 里只有 2 个声明 `allowed-tools`，建议在 DSH 的 skill 模板/校验里把 `allowed-tools` 作为推荐字段。

对工具本身：下一步可以把 L02/L07 也做成“代码块上下文感知”（本次 L03 已这样做），并加一个基于执行沙箱的动态检查通道；静态规则继续维持高精度、低噪声。
